Reverse-engineering · theHunter: Call of the Wild

The Ghost Species

A mission-reward species that vanishes on save. No tools, no symbols, no documentation. One week from first look to root cause, reproduction, and disclosure in a binary of ~90,000 functions.

theHunter: Call of the Wild's Scotland DLC unlocks the Wild Haggis after a specific mission. Finish the mission, and haggis should start appearing on the map.

Players reported otherwise: complete the mission, save, reload, and no haggis. Those who stayed online saw them fine; those who saved and reloaded saw nothing, permanently. The community had documented the pattern but not the cause. That's where I started.

The binary is a 37 MB executable holding 25 MB of code: roughly 90,000 functions, no symbols, no debug information; 133 loaded modules and 6 GB of memory at runtime. Thirteen of those functions turned out to matter. Finding them, and proving they were the right thirteen, was most of the work.

The game packs its assets into archive files: a .tab index and an .arc container. Mission definitions, reward configurations, and species parameters all live inside, not as normal files. A parser for the format gave me the mission definition for the haggis unlock, including the reward entry that specifies which species to enable and what hash to write, a concrete anchor to trace through the binary.

The second source was the save file: a compressed, schema-driven binary format with no existing parser. I built one: the container format, the compression layer, and the schema definitions that describe each data type's layout. Once it could read population data, the save became a window into the game's live state.

Save format internals

Each species is stored as a population entry with a fixed-stride record layout:

SAnimalPopulationSaveData
┌─────────────────────────────────────────────────────────────┐
│ NameHashId          : u32          species identifier        │
│ Groups              : array        group definitions         │
│ RepopulateData      : array        template for new groups   │
│ Revision            : u32          version counter           │
│ ConditionsFulfilled : array<u32>   hashes gating spawning     │ ◀── the
└─────────────────────────────────────────────────────────────┘     critical
                                                                     field

The save system uses a generic schema-driven serializer: it doesn't know what ConditionsFulfilled means, it just reads the schema and serializes the field. This becomes relevant later.

Each population entry carries a field called "conditions fulfilled", a list of hashes. For most species it's empty. For the haggis, after mission completion, it holds a single hash. That was the first thread worth pulling.

Tracing the reward

Where does that hash come from? The save told me what was stored, not who writes it. Starting from the population writer, the function that appends to the conditions list, I followed call references upstream through a three-function chain:

event_handler(event_data)
  │ reads reward_hash from event payload
  │
  └──▶ reward_executor(reward_entry)
        │ processes cash, XP, unlocks
        │ reads target species from reward definition
        │
        └──▶ population_writer(species, reward_hash)
              │ dedup check against existing entries
              │ appends reward_hash to conditions_fulfilled
              └──▶ mark save dirty

Direct static calls, no vtable indirection. The mission reward writes one specific hash into the haggis conditions list. But something has to read it.

The dispatcher routes each species by whether save data exists; a cleanup routine then syncs the in-memory save structures with live state; a per-species scheduler timer gates spawning through a condition check that reads the conditions-fulfilled list. For the haggis, a save entry always exists, even with zero groups, so it always takes the load path. The fresh path, which could bypass the gate, is never reached.

The gate check: pseudocode 
def gate_check(species_data, save_data):
    gate_entries = species_data.gate_requirements

    if not gate_entries:        # no restrictions for this species
        return PASS

    for entry in gate_entries:  # haggis has exactly one
        required = entry.required_condition_hashes

        if not required:        # gate entry with no requirements
            return PASS

        if all(h in save_data.conditions_fulfilled for h in required):
            return PASS

    return FAIL                 # no gate entry fully satisfied

For haggis, this reduces to:

  reward_hash in conditions_fulfilled?
          │                │
         YES              NO
          │                │
          ▼                ▼
     gate PASS        gate FAIL
     → spawn          → skip
     → haggis         → timer resets
       appear           → check again in ~61 min
                        → still empty
                        → FAIL
                        → forever

The reward writes a hash to the conditions list; the gate reads that list to allow spawning. The two values match, proven by the fact that haggis do spawn for players who stay online. The system is designed to work. So where does it break?

The destruction point

Instrumenting the cleanup routine answered that. It runs on every load, in two steps: first it frees and zeros the conditions-fulfilled list for every species; then it discards those entries and rebuilds from live zone data, copying groups, repopulation templates, and metadata. It does not copy conditions-fulfilled: zone data never carries that field, so the rebuilt entries are created without it.

FieldBeforeAfter cleanup
NameHashId0x7eb7edf90x7eb7edf9 ✓
Groups[] (empty)[] (empty) ✓
RepopulateData1 entry1 entry ✓
Revisionsetset ✓
ConditionsFulfilled[reward_hash][] ✗ destroyed
Cleanup routine: pseudocode 
def cleanup(population_manager):
    save_entries = population_manager.save_data

    # Step 1: destroy all conditions data
    for entry in save_entries:
        free(entry.conditions_fulfilled)    # release memory
        entry.conditions_fulfilled = empty  # zero pointers

    # Step 2: reset save vector
    save_entries.clear()

    # Step 3: rebuild from live state
    for species in population_manager.zone_data:
        new_entry = serialize(species)
        # copies: groups, repopulate_template, metadata
        # does NOT copy: conditions_fulfilled
        # (zone_data doesn't carry this field)
        save_entries.append(new_entry)

The rebuild creates entirely new entries from the live game state (zone data). Zone data doesn't carry conditions-fulfilled; that field only exists on save entries. So the new entries are built from a source that never had the field, not from a zeroed value.

So the reward writes the hash, the save persists it to disk, the deserializer restores it into memory, and cleanup destroys it before the scheduler ever reads it.

Why it's permanent

"Cleanup destroys the hash" explains one failed spawning cycle. Permanence needs no recovery path. Three routes, all blocked:

  All recovery paths closed. Damage is permanent.

The rebuild builds from zone data, which never carries the field. The scheduler has a skip counter that can bypass the gate for periodic unconditional respawning, but a flag keeps it from ever incrementing for haggis. The mission is one-shot; once the reward fires it can never fire again. Every save overwrites the file with the corrupted data; every load runs the same cleanup. The haggis entry sits with zero groups and an empty conditions list, permanently.

The timer

The player has to stay online, without saving, until the timer fires after completing the mission. Anyone who finished the mission quickly after loading has a large remaining window, and saving inside it destroys the hash on the next load. Players who spent time on the menu, loading, or exploring first often had the timer fire early and avoided the bug; players who rushed triggered it almost every time: a subtle ordering dependency that hits a large fraction of players with no visible pattern.

Proving it

Proof meant watching it happen end to end, with every intermediate state captured. I built a reproduction harness: thirteen functions hooked across the population lifecycle, save synchronization, scheduling, and the reward chain, with a monitor loop polling every five seconds. The spawning timer was patched at runtime to compress the 60-minute wait to 30 seconds without touching the binary on disk: same mechanics, only the clock changes. Two phases: capture a save with the hash written and the timer set never to fire, then reload with the timer compressed and all thirteen hooks live. The trace told the story:

[LOAD]            conditions_fulfilled = [reward_hash]  ← deserialized from save
[CLEANUP]         conditions_fulfilled = [reward_hash]  ← still present
[CLEANUP fires]   → clear all conditions lists
[REBUILD]         groups=0, conditions omitted → conditions_fulfilled = []
[MONITOR  t+5s]   conditions_fulfilled = [], timer = 24.6s
[MONITOR t+10s]   conditions_fulfilled = [], timer = 19.6s
  ...
[MONITOR t+25s]   conditions_fulfilled = [], timer =  4.6s
[GATE]            check #1 → FAIL (expected reward_hash, found empty list)
[MONITOR t+30s]   conditions_fulfilled = [], groups = 0, permanent

Save-file forensics confirmed it from the other side: the data survived to disk with the hash intact, and was destroyed in memory on the next load. The reproduction is 100% reliable.

Root cause

An implicit ordering dependency between two systems that don't know about each other.

The condition hash is transient state that bridges mission completion and the next spawning cycle, and the save system treats it as discardable. Complete the cycle before a save/reload and the hash is consumed normally, groups are created. Let a save/reload intervene and the hash is destroyed, and the bridge collapses.

The disclosure

The full investigation went to the studio through their official support channel: root cause, reproduction steps, save-file comparisons, plus a second unrelated bug found along the way. They relayed the report to QA, reproduced the issue from it, and publicly confirmed the bug with a committed fix.

Method withheld

This write-up shows the investigation and the proof. It deliberately omits the specifics that would let someone reproduce the tooling: exact function addresses, struct offsets, the hook set, and the save schema. The pattern is the point; the coordinates are mine.

The pattern

A specific instance of a general failure mode: state loss across a serialization cycle. Any system that saves and restores state (game saves, database checkpoints, container snapshots, session persistence) can carry it. Transient data that lives between two processing steps gets discarded by a serialize/deserialize cycle that doesn't know the data matters.

The method transfers too: static analysis for a structural map, dynamic instrumentation to observe real behaviour, targeted reproduction to confirm causality, proof by contradiction to close escape routes. The specific technology is incidental.

The destruction happens inside a routine whose job is to maintain consistency: not a crash, not a failed write, not a missing null check, but a well-intentioned synchronization step that doesn't account for data it was never told about. Bugs that look correct are the ones that survive shallow investigation.
