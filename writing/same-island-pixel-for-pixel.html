Reverse-engineering · Rust, Facepunch Studios

Same island, pixel for pixel

Rust's world is generated by a closed-source native library with no public spec. I reverse-engineered and reimplemented it from scratch. Output: byte-for-byte identical to the game's. Then I forked the exact version, dropped the exactness on purpose, and took the same pipeline from 140.6 s to 20.6 s.

Rust generates its world from a seed (coastline, rivers, lakes, biomes, monuments) deterministically: same seed, same island. The generator is a closed-source native library shipped with the game; no public spec, no reference implementation. I rebuilt it from scratch with no access to the source.

The bar: bit-exactness

A visual look-alike proves nothing. The test is bit-exactness, and it's hard because floating-point addition isn't associative: the same operations in a different order return a different answer. You match the arithmetic operation-for-operation, or you don't match at all.

Example 3: the way out, and the trap

Example 1 diverges in the sixteenth digit; example 2 flips clean between 1 and 0; example 3 shows the cure: a wider type, and the lost addition comes back. That cure is the catch: every trick that makes the math more accurate makes it less like the game's. Reproduction runs the other way: match the exact widths and the exact order, and keep every rounding error the original makes. Across a million cells, one wrong bit is the difference between identical and mismatched.

Not a speedup for the game

The cost is elsewhere, in single-threaded managed work; a faster generator would save time nobody waits on. Nothing below changes that. This is proof of understanding, not a patch for Rust.

It does leave a question the exact version is structurally unable to answer: how fast could this pipeline be if it didn't have to be exact? Every fast answer is illegal under bit-exactness. Fewer iterations, a cheaper heuristic, f32 where the original widened to f64, a GPU: each one moves bytes, and not moving bytes was the whole contract. So I forked it.

The fork that deletes the guarantee

The fork starts as a byte-copy of the exact port and then breaks it on purpose. It is allowed to generate a different island from the same seed. Determinism survives (the same seed still gives the same island as itself) but fidelity to the game is gone, and with it the oracle that made every claim above checkable.

That is the part worth being careful about. Losing the oracle is where optimisation work quietly starts lying to itself: with no definition of correct, every change is an improvement. So the replacement contract was written down before anything was touched.

What "correct" means once bit-exact is gone

A map is correct when it is structurally valid and playable. Five invariants replace byte-equality, and a lever is legal no matter how many bytes it moves as long as it keeps all five:

  1. Deterministic per seed: same seed and size, same map, every run. Parallel work must use a fixed reduction order.
  2. Monuments don't overlap: placed bounding boxes don't intersect, and each sits on terrain flattened to its footprint.
  3. The road and rail graph is connected: routes reach their intended endpoints, splines are continuous, terrain is carved under them.
  4. Biome, topology and spawn fields are sane: biome regions contiguous, cliffs and water classified, decor on valid ground rather than underwater or mid-air.
  5. In-bounds and finite: no NaN or infinity in any raster, every value in engine-valid range, heightmap continuous with no seams.

Two of the five are machine-checked on every run: determinism, by fingerprinting two runs of three different seeds, and finiteness, across every raster the pipeline emits. The other three are added to the test file as a lever lands that could break each one, rather than built ahead of need, so the honest statement is that the levers which changed the map were checked by rendering the map and looking at it. That is weaker than maxULP = 0. Deliberately, and it is the price of everything below.

The bit-exact strategy then hits a floor no output-identical transform can cross, dominated by the cliff-placement sweep and hydraulic erosion, which is what motivated dropping the contract in the first place.

Two of those were bugs, not tuning knobs

The pathfinder was barely steering. Roads and rails route with A*, which is only faster than an exhaustive search because its heuristic estimates the remaining cost well enough to aim at the goal. The routine I reproduced estimated with Chebyshev distance times one, while the edge costs on that same grid run 10² to 10³ per cell. An estimate two or three orders of magnitude under the truth is still admissible, so the routes it returned were optimal; it just wasn't pointing anywhere, and the search spread outward almost like plain Dijkstra. Scaling the estimate by the smallest positive cell cost on the map, computed once, is still a strict lower bound, so paths stay optimal and the connected-graph invariant held, but the frontier collapses toward the goal. Rail routing went 3.4 s → 0.1 s, the largest single lever in the campaign.

The circle test never rejected anything. Ninety-five percent of the CPU in the river stage was one function: a disc scan over the topology map, an ~87×87 box OR'd at every four-metre step, about 1,250 steps per river walk. Inside it, a distance in cell units was compared against a radius in metres. The units didn't match, so the test never excluded a cell; it read the entire square, every step, forever. Once you know it is a square and not a disc, the answer is a prefix-OR table: four reads instead of ~7,500. Wall time 5.84 s → 1.23 s, CPU time 145 s → 25 s. Bit-exact, because the code had been computing the square all along.

Neither was found by reading. Both were found by profiling something I already understood line by line, which is the whole argument for building the exact version first.

The ceiling is not the core count

The box is an i9-14900K: eight performance cores, sixteen efficiency cores, 36 MB of L3. The maps these stages stream are about 80 MB. Once a pass is reading more map than fits in cache, extra threads stop helping and start hurting.

Uniform cliff scatter, seconds1.620.571.012.43

Thirty-two threads is slower than one. Two effects compound: the pass is memory-bandwidth-bound, so past about four threads the cores queue on a single memory controller; and it is multi-resolution, which means thirty-two checkerboard barriers, and past eight threads the work spills onto efficiency cores so every barrier waits for the slowest of them. Capping it to a four-thread pool took it 1.58 → 0.56 s. The dense scatter beside it is flat from four threads to thirty-two: already saturated, nothing there to win.

Generalised: any stage streaming the 80 MB maps gets roughly 4× of parallelism, not 32×. Giving each thread its own copy of the maps does not help, because there is still one memory controller. At the point this was measured, 65% of the remaining wall clock was running at under two-way parallelism, and the naive "total CPU ÷ 32" floor was simply not reachable for the bandwidth-bound half of it.

Which is the actual case for the GPU. Not that it is faster, but that it has different memory.

The GPU port

The card is an RTX 4080 SUPER: roughly 736 GB/s of memory bandwidth against the CPU's ~50 GB/s. That ratio, not the core count, is the reason the port was worth building.

The backend is cudarc against CUDA 12.3, loaded dynamically at runtime rather than linked at build time. There is no build.rs, so the binary compiles on a machine with no CUDA toolkit installed and falls back to the CPU path when there is no device. Kernels are compiled by NVRTC at startup: about 0.35 s, once, amortised across every stage that later moves onto the device.

Explicitly not bit-exact: the kernels use fast-math and floorf, with no ULP matching against the CPU version. Determinism survives anyway, because GPU float operations are run-to-run identical on the same device, which is invariant #1, the fork's bar, not the old one.

The measurement that decided where to stop. The obvious plan is "put the world generator on the GPU". Profiling said the noise was never the problem: height, biome, splat and topology classification together are about 1.08 s of clean per-pixel work, exactly what a GPU eats, and projecting the measured height speedup puts that near 0.1 s. But dilate-and-flood is 0.694 s, which is 96% of the topology stage, and its tail is a serial breadth-first flood fill. That is inherently sequential and GPU-hostile. Porting the easy 1.08 s leaves the 0.694 s exactly where it was. So the GPU work stopped there, because the profile said so, not because the port got difficult.

What didn't work

Seven levers were built, measured, and then reverted or refuted. Each one carried an estimated speedup in the ledger before it was written. They are published because the failures are what make the successes worth reading.

Six of the seven are one finding, and it is the most useful thing the fork produced.

The maps these passes write are not outputs. They are inputs. The placement map looks like bookkeeping: a record of where things ended up. It is actually negative feedback: every stamped cliff blocks roughly 97% of the candidates near it. Freeze it so threads can read it without contention and the pass stops suppressing itself. It accepted 1,265 cliffs where the serial version accepted 37, a 34× over-acceptance, which is both a flat violation of the non-overlap invariant and catastrophically slow, because each accepted root drags a ~116 ms recursion behind it.

On the decor pass the same map was quietly doing a second job nobody had written down: it was the cheap early rejection that skipped the expensive gate chain. Freezing it didn't only change the answer, it multiplied the work elevenfold. The follow-up version that carefully restored the exact object count still ran 11× the CPU, because the count was never the thing the map was protecting.

The rule that came out of it: parallelise outer independent samples, the keep-the-best-of-N shape, and never freeze a serial pass that mutates a map the same pass reads back.

Scope & framing

Independent engineering research against a game that ships its managed code unobfuscated for modding, run on a headless dedicated server. It reproduces behaviour to verify understanding; it is not a redistribution of the studio's code, and not a cheat or exploit. The fork goes further from the game rather than closer: it is a separate program that generates its own maps and no longer matches Rust's at all. No studio relationship is claimed, and the speed figures are measurements of my own implementation, not of anything Facepunch ships. The proof is self-verification against the live game.

The pattern

Reconstruct the process behind a closed binary precisely enough to reproduce its output exactly: the arithmetic, not just the shape. The same discipline finds why a shipped game crashes on one machine, or where a data pipeline's numbers go wrong.

The fork is the second half of the same discipline. Once the pipeline was fully mine, making it fast stopped being a matter of knowing tricks and became a measurement problem, and measurement is what caught the mis-scaled heuristic, the circle test that never rejected, the 33.6 MB copy inside a loop, and four confident parallelisations that were slower than doing nothing. Optimisation that isn't measured produces precisely those four, and ships them.
