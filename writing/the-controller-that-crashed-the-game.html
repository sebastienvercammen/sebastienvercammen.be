Reverse-engineering · theHunter: Call of the Wild

The controller that crashed the game

Plug in a DualShock 4 and the game crashed to desktop about three seconds after launch, every time. The obvious fix cleared that crash and uncovered a second one, deeper in. I fixed the root cause and eliminated both, audio intact.

On some players' machines, theHunter: Call of the Wild crashed to desktop a few seconds after launch; on others it ran fine. The variable was a single peripheral: a DualShock 4 controller in a USB port. Attach it and the window vanished about three seconds in, straight to desktop, no dialog. Unplug it and the game booted normally.

InputLaunch resultRate
DualShock 4 attachedCrash to desktop, ~3 s in ✗100%
No controllerBoots to menu ✓0%

One binary input, one deterministic outcome, on a fixed timeline. The controller's presence routes execution down a path the game otherwise never takes, and that path dies.

The trace

The failure was a jump to a garbage address, the signature of a virtual call through an object whose function-table pointer was never set. The object belonged to the audio system: the game's FMOD Studio integration. With the controller attached, boot reached that object before its vtable pointer had been written, and the first call through it jumped to whatever happened to be in that memory.

Three seconds is roughly how long boot takes to reach that first call. Without the controller, the path is never taken and the uninitialized object is never touched.

Method withheld

This write-up shows the symptom, the impact, the diagnostic reasoning, and the proof. It deliberately omits the method: how the faulty object was located, how its state was corrected, the exact trigger and mechanism behind the fix, and any tool internals. The class of the bug (an uninitialized function-table pointer in an audio object) is the transferable part. The coordinates and the mechanics stay mine.

The obvious fix was a relocation

Making that first call survive did clear the three-second crash: the controller-attached launch sailed past the old failure point and reached the menu. But about twenty-eight to thirty seconds in, the game crashed again: a second, distinct failure cascading from the same half-initialized state. The first crash had been masking it.

A fix that creates a new failure isn't a fix; it's a relocation: a crash you can see traded for one you can't, moved into the menu where it looks like a different bug.

Both crashes, gone

The target was the object's state, not the call site. Once the audio object was in the condition it was always meant to be in before anything called through it, both failure points disappeared at once, and sound still worked. Neutering the audio path would have traded a crash for silence; the bar was both crashes gone and audio fully intact.

Acknowledgment

I passed the findings to the studio through a contact there, a private exchange rather than a public patch note. The contact (COTW_Vivi) wrote back that they had "relayed your message to our QA and it helped them reproduce the issue… my sincerest gratitude." A report that lets a studio's own QA reproduce the failure is the outcome that matters: the description of what was wrong was precise enough to act on.

The pattern

Two things generalise. A half-constructed object with an uninitialized pointer looks fine until a specific input (here, one controller being present) routes the first call through the empty slot and it jumps to garbage; the tell is a crash address that was never a function. And a fix that creates a new failure isn't done: fix the state that produced the symptom, then verify the whole flow past the original crash, not just the one you can see.
