Reverse-engineering · Windrose

The startup crash in the runtime

A slice of Windrose players hard-crashed before the main menu, and the crash never once reproduced on the team's own machines. The fault sat below the game, in the shipped DirectX 12 runtime. The studio adopted the fix into their official docs and credited me by name.

Game Windrose · playwindrose.com Engine Unreal Engine 5 · D3D12 Access shipped build, no source Outcome fixed · publicly credited by name
D3D12Core.dll update … huge kudos to our friend @Seb for figuring this one out! ❤️Windrose team · official FAQ / Dedicated Server Guide

Windrose is a custom Unreal Engine 5 build on D3D12. A slice of players hard-crashed on startup, before the menu drew a single frame, and the crash never reproduced on any developer workstation, QA box, or configuration the studio could point at.

That property is the clue. A crash that depends on whose machine it runs on, not on which build, isn't in the game's logic; the logic is identical for everyone. The fault was below the game, in the layer it starts on top of.

Below the game

A D3D12 title hands rendering to the DirectX 12 runtime that ships alongside it and loads on every player's machine: code the studio doesn't write or compile, versioned independently of the game.

The crash root-caused there: environment-sensitive exactly as the field reports described, invariant to the game build. With the corrected D3D12Core.dll in place, the affected machines boot to the menu normally: same build, same players, no crash. The fix is a runtime update, not a game patch.

Method withheld

This shows the symptom, the reasoning that placed the fault below the game, and the fix the studio shipped. It omits how the crash was cornered on machines where it refused to reproduce, the instrumentation that isolated it to the runtime, and what in the environment triggered it. The public credit is the proof; it is not a reproduction guide.

The proof isn't my own reproduction or a self-graded check. The people who own the game confirmed the diagnosis publicly, by name, and shipped it to their players.

Second front: frame hitches

The same engine had a separate problem. In dense scenes the frame time spiked: sporadic stalls in the multiple-hundred-millisecond range, each a visible hitch.

Median and p99 are fine; the game runs smooth almost all the time. The damage is entirely in the tail: a worst single hitch over a full second, plus a recurring cluster of 263–289 ms hitches at roughly 20 per minute. Averages hide it. The obvious suspects each had to be ruled out, in order:

Step ③ is the whole diagnosis: a busy render thread is a workload problem you cut; a blocked one is a stall, waiting on something else. Here it was blocked, waiting on the runtime compiling a shader pipeline on demand, the first time a material variant appears, paid once, cheap forever after. That is why the hitches cluster when the scene churns through fresh material. The scene was not small:

The pattern

Both fronts had their real cause below the game's own code, in the shipped graphics runtime. The crash never reproduced in-house because the fault wasn't in the build; the hitch survived every workload cut because the render thread wasn't busy, it was blocked. The answer appeared only once the investigation followed the failure past the game's boundary into the runtime it depends on, and proved it well enough that the people who own the software shipped the fix and put their name next to mine.
